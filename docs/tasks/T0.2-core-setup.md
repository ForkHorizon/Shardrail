## Decoupling & Fixes Applied
1. **Decoupling `crates/shardraild` from `crates/relay`**:
   - `shardraild` had an integration test `tests/relay_tunnel.rs` that previously depended on `crates/relay` (Actix-web server).
   - Removed `shardrail_relay` from `crates/shardraild/Cargo.toml`.
   - Created `crates/shardraild/tests/common/mock_relay.rs`: a lightweight standalone Tokio/WebSocket mock relay implementing the exact tunnel protocol, handshake, authentication tokens, and routing.
   - Refactored `tests/relay_tunnel.rs` to use `mock_relay::RelayRuntime`.
   - Result: Zero Actix-web dependency in `Shardrail_Core`, clean boundaries, and all tunnel tests pass.
2. **Removing foreign git root bindings and hard-coded paths**:
   - Rewrote `crates/shardraild/build.rs`: eliminated `git rev-parse --show-toplevel` execution. The build script now resolves workspace root dynamically relative to `CARGO_MANIFEST_DIR` (`../../`) with runtime environment variable overrides (`SHARDRAIL_REPO_ROOT`, `SHARDRAIL_GIT_DIR`, `SHARDRAIL_S1_TESTREPO`).
   - Updated `crates/shardraild/src/session_workdir.rs` to support `SHARDRAIL_REPO_ROOT` and `SHARDRAIL_S1_TESTREPO` overrides cleanly while retaining backward-compatible test allowances.

## Contract & Client Publishing Decision Note
**Decision**: Publish `@shardrail/contracts` and `@shardrail/client` to consuming repositories (`Shardrail_Web`, mobile clients) via **versioned Git release tags (`git+https://github.com/ForkHorizon/Shardrail_Core.git#v<version>&path:packages/<pkg>`) and GitHub Release tarball assets**.

**Justification**:
1. **Zero Registry Friction**: Does not require maintaining private npm package registry tokens or publishing public npm modules before the project is ready for public release.
2. **Immutable Provenance**: Every consumer pin (`v0.0.1-import`, `v0.1.0`) is cryptographically tied to the exact Git commit, tag, and protocol schema in `Shardrail_Core`.
3. **No Drift / No Vendoring**: `Shardrail_Web` imports contracts directly as an external versioned dependency in `package.json`, completely eliminating duplicate type files.
4. **CI Compatibility**: GitHub Actions and standard npm/pnpm can fetch git-pinned packages directly without authentication setup on public repositories, or via standard GitHub deploy tokens.
5. **Future Transition**: When ready for npm publishing in later stages (N2), only `package.json` version strings need updating; the package build and consumption model remains identical.

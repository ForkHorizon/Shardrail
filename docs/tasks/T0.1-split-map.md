## 3. Cross-Component Dependency Analysis

### 3.1 Relay ↔ Shardraild
- **Role Separation:**
  - `shardrail_relay` is a blind WebSocket routing server. It routes opaque envelopes between browser clients and daemons based on `machine_id` and `client_id`. It has **no dependencies** on `shardrail-protocol`, `journal`, or `session-core`.
  - `shardraild` connects outbound to relay via `src/relay_dialer.rs` using `tokio-tungstenite`.
  - Payloads traveling through the relay are end-to-end encrypted with Ed25519/X25519 keys shared only between the browser and the daemon. The relay cannot decrypt or inspect messages (D69, D70).
- **Test Coupling Finding:**
  - In `crates/shardraild/Cargo.toml`, `shardrail_relay = { path = "../relay" }` is included under `[dev-dependencies]` solely for the integration test in `crates/shardraild/tests/relay_tunnel.rs`, which spins up an in-process `RelayRuntime`.
- **Resolution for Split:**
  - In `Shardrail_Core`, `crates/shardraild/tests/relay_tunnel.rs` will be updated to use a minimal in-memory mock WebSocket tunnel server (or lightweight test fixture), eliminating the dev-dependency on `crates/relay`.
  - True full-stack relay tunneling tests will execute in `Shardrail_Web` CI, where the relay runs against the prebuilt `shardraild` binary.

### 3.2 UI ↔ Protocol (via `packages/contracts`)
- **Consumption:**
  - The React UI imports message DTOs and event models directly from `@shardrail/contracts`:
    - Session events (`SessionCreated`, `SessionUpdated`, `SessionTurnAdded`, etc.)
    - Protocol messages (`ClientHello`, `ServerHello`, `ApprovalRequest`, `ApprovalResponse`, etc.)
- **Generation:**
  - `crates/protocol` exports `schema/contracts.schema.json` via its `export-schema` binary.
  - `packages/contracts` uses `json-schema-to-typescript` (`npm run generate`) to produce `packages/contracts/src/generated.ts`.
  - Drift is strictly prevented by `scripts/check-schema-drift.sh`.
- **Resolution for Split:**
  - `packages/contracts` lives in `Shardrail_Core`. It is published or packaged for consumption by `Shardrail_Web`.

### 3.3 UI ↔ `packages/client`
- **Consumption:**
  - The UI uses `@shardrail/client/browser` (`packages/client/src/browser.ts`) for:
    - Ed25519 key generation and storage via WebCrypto in IndexedDB (with `@noble/ed25519` fallback).
    - Transcript framing and cryptographic signing of the handshake.
    - WebSocket connection management (connecting either directly to daemon loopback or through the relay).
- **Current Link:**
  - `apps/s5-prototype/package.json` specifies `"@shardrail/client": "file:../../packages/client"` and `"@shardrail/contracts": "file:../../packages/contracts"`.
- **Resolution for Split & Contracts Publishing Method:**
  - We evaluate the two approaches mandated for decision in T0.2:
    1. **Option A: npm Package (GitHub Packages / npm Registry)**: Publish `@shardrail/contracts` and `@shardrail/client` with semantic versioning (e.g. `v0.1.0`). Web consumes `"@shardrail/contracts": "^0.1.0"`.
       - *Pros:* Standard JS ecosystem dependency model; clean separation; lockfile-friendly; zero subpath git clone overhead.
       - *Cons:* Requires publishing step and auth token in CI.
    2. **Option B: Versioned Git Dependency (`git+https://...#v0.0.1-import`)**:
       - `package.json` entry: `"@shardrail/contracts": "git+https://github.com/ForkHorizon/Shardrail_Core.git#v0.0.1-import"` (using npm workspace subpath support or tagged releases).
       - *Pros:* Direct link to git commits/tags without external package registry setup.
       - *Cons:* Slower npm installs; npm requires building generated TypeScript if dist is not committed; subdirectory git dependencies can be fragile across npm versions.
    3. **Option C: Packaged Tarball Release Artifacts (`@shardrail/contracts-0.1.0.tgz`)**:
       - Core CI attaches packed `.tgz` artifacts to GitHub Releases; Web pulls them via URL or vendored package in CI.
  - **Recommendation:** **Option A via GitHub Packages (or tagged npm release)** as primary, with a self-contained tarball release fallback. During early bootstrap of T0.2/T0.3, versioned git tag or release tarballs can be pinned cleanly.

### 3.4 UI (`apps/s5-prototype`) ↔ `s5-swift` & `src-tauri`
- **`s5-swift`:**
  - Audit confirms **0 imports, 0 calls, and 0 references** to `s5-swift` from `apps/s5-prototype`.
  - `s5-swift` was an isolated SwiftPM prototype for macOS performance benchmarks. It has zero coupling to the Web UI.
- **`src-tauri`:**
  - `apps/s5-prototype/src/main.tsx` contained conditional Tauri shims:
    ```ts
    import { listen } from '@tauri-apps/api/event';
    import { Channel, invoke } from '@tauri-apps/api/core';
    const browserMode = !('__TAURI_INTERNALS__' in window);
    ```
  - In browser mode (`browserMode = true`), all Tauri APIs are bypassed; the application interacts exclusively with `@shardrail/client/browser`.
  - Only `tauri-bench.test.ts` and `ui-config.test.ts` referenced Tauri configuration files (`tauri.conf.json`).
  - **Resolution:** In T0.3, `src-tauri`, `tauri-bench.test.ts`, and `@tauri-apps/*` dependencies will be moved out of the active tree into the archive branch. The UI will run purely as a modern Vite SPA.

## 4. Hard-Coded Paths and Split Breakages

The following hard-coded paths and assumptions currently exist and will break upon repository split:

### 4.1 Rust Daemon & Build Script (`crates/shardraild`)
1. **`crates/shardraild/build.rs`**:
   - Compiles repository metadata using `git rev-parse --git-common-dir`.
   - Exports environment variables:
     - `cargo:rustc-env=SHARDRAIL_REPO_ROOT=<path>`
     - `cargo:rustc-env=SHARDRAIL_GIT_DIR=<path>`
     - `cargo:rustc-env=SHARDRAIL_S1_TESTREPO=<path>/spikes/s1-testrepo`
   - *Impact after split:* In `Shardrail_Core`, `spikes/s1-testrepo` will not exist.
2. **`crates/shardraild/src/session_workdir.rs`**:
   - Reads `env!("SHARDRAIL_REPO_ROOT")`, `env!("SHARDRAIL_GIT_DIR")`, and `env!("SHARDRAIL_S1_TESTREPO")`.
   - Validates that agent session working directories are outside the repository checkout (`shardrail_prefix_rejected`), except for the hardcoded `spikes/s1-testrepo`.
   - *Fix in T0.2:*
     - Strip the hard-coded `spikes/s1-testrepo` exception from `build.rs`.
     - Allow specifying test repositories via environment variable (`SHARDRAIL_ALLOWED_TESTREPO`) or CLI flag (`--allow-workdir`).
     - Bind safety check dynamically to the Core checkout root.

### 4.2 Scripts (`scripts/*`)
1. **`scripts/dev-try.sh`**:
   - `BIN="$ROOT/target/debug/shardraild"` (assumes daemon is in current tree).
   - `ASSETS="$ROOT/apps/s5-prototype/dist"` (assumes UI is in current tree).
   - `WORKDIR=${SHARDRAIL_SESSION_WORKDIR:-$SHARDRAIL/spikes/s1-testrepo}`.
   - Executes both `cargo build -p shardraild` and `npm --prefix apps/s5-prototype run build`.
   - *Impact after split:* Cannot build both from one repo. Script will be refactored: Web's `dev-try.sh` will accept `SHARDRAILD_BIN` pointing to a local Core build or release binary.
2. **`scripts/check-schema-drift.sh`**:
   - `cargo run --quiet -p shardrail-protocol --bin export-schema`
   - `npm --prefix packages/contracts run generate`
   - `git diff --exit-code -- schema/contracts.schema.json packages/contracts/src/generated.ts`
   - *Impact after split:* Lives entirely in `Shardrail_Core`. All paths remain valid within Core.
3. **`scripts/check-daemon-test-orphans.sh`**:
   - Paths point to `$repo_root/target/debug/shardraild`, `$repo_root/target/debug/shardrail-fake-acp`, and `$repo_root/crates/shardraild/tests/fixtures/fake_codex_app_server.py`.
   - *Impact after split:* Lives entirely in `Shardrail_Core`. All paths remain valid within Core.
4. **`scripts/check-npm-licenses.mjs`**:
   - Inspects `../packages/contracts/package-lock.json` and `../packages/client/package-lock.json`.
   - *Impact after split:* Lives in `Shardrail_Core`.

### 4.3 UI Configuration & Tests (`apps/s5-prototype`)
1. **`apps/s5-prototype/package.json`**:
   - `"@shardrail/client": "file:../../packages/client"`
   - `"@shardrail/contracts": "file:../../packages/contracts"`
   - *Impact after split:* Breaks immediately when packages move to Core. Replaced by versioned package/git dependency.
2. **`apps/s5-prototype/tests/browser-e2e-server.mjs`**:
   - `const binary = resolve(process.env.SHARDRAILD_BIN ?? '../../target/debug/shardraild');`
   - `const fakeAcp = resolve(process.env.SHARDRAIL_FAKE_ACP_BIN ?? join(dirname(binary), 'shardrail-fake-acp'));`
   - *Impact after split:* Fails in isolated Web clone. E2E tests must fetch the `shardraild` + `shardrail-fake-acp` binaries from a Core release or configured environment variable (`SHARDRAILD_BIN`).
3. **`apps/s5-prototype/tests/ui-config.test.ts`**:
   - Reads `../src-tauri/tauri.conf.json`.
   - *Impact after split:* Breaks once `src-tauri` is moved to archive. Archiving Tauri removes this test.

### 4.4 CI Workflows (`.github/workflows/ci.yml`)
- Current monolithic workflow runs both Cargo checks for the whole workspace (including `crates/relay`) and npm checks for packages.
- *Impact after split:*
  - `Shardrail_Core` CI will run: `cargo fmt`, `cargo clippy`, `cargo test`, `cargo deny`, `scripts/check-schema-drift.sh`, client typecheck and client tests.
  - `Shardrail_Web` CI will run: `cargo test -p shardrail_relay`, UI build (`npm run build`), UI tests (`npm test`), and browser E2E tests using the Core release binary.

## 6. Risks and Mitigations

| Risk | Impact | Mitigation Strategy |
|---|---|---|
| **R1: Circular or Broken Contract Dependency** | Web cannot build without Core; version drift causes runtime handshake failure. | Define contracts strictly in Core; publish with semantic tags; Core CI runs drift verification (`check-schema-drift.sh`); Web CI locks exact version. |
| **R2: Test Breakage in Core from Missing Relay** | `crates/shardraild/tests/relay_tunnel.rs` fails when `crates/relay` is moved to Web. | Refactor `relay_tunnel.rs` in Core to use a self-contained test WebSocket mock for local tunnel verification; full integration runs in Web. |
| **R3: Test Breakage in Web from Missing Daemon** | Web Playwright E2E tests cannot spawn `shardraild` or `shardrail-fake-acp`. | In Web CI, download the prebuilt `shardraild` binary from the matching `Shardrail_Core` GitHub release tag, or allow specifying `SHARDRAILD_BIN`. |
| **R4: Workdir Security Bypass Regression** | Removing `SHARDRAIL_REPO_ROOT` from `build.rs` could inadvertently allow agent execution in protected root directories. | Replace compile-time `build.rs` git inspection with deterministic runtime canonical path checks that fail closed on repo root, home, and system roots, while supporting explicit allowlisted test directories. |
| **R5: Loss of Historical Wave Artifacts** | Removing `spikes/` and `archive/` deletes context wanted for future debugging. | Do not permanently delete files during initial migration: create an `archive/legacy-spikes` branch in `Shardrail_Web` before cleaning `main`. |

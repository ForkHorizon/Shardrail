## 1. Channels (D6)

| Agent | Channel used | Deliberately not used |
| --- | --- | --- |
| Grok Build (1.0.52 on the planning machine) | `grok agent stdio`, ACP v1 (adapter dual-stack v1/v2, D35) | headless `-p` as an interactive channel; parsing `~/.grok/sessions` as an API; `grok agent serve`/`leader`/`headless` modes; `--always-approve` |
| Hermes Agent (0.21.6) | `hermes acp` / `hermes-acp`, ACP v1 (dual-stack adapter, D35) | gateway, cron, kanban, Hermes desktop |
| Codex CLI (0.160.0) | separate child `codex app-server` over stdio (the command itself is documented as experimental and "not supported for production workloads" — accepted risk R1) | WebSocket transport (experimental, unsupported); `codex exec` as a UI session; shared `app-server daemon`/`proxy` used by the user's TUI; every `experimentalApi` method (D36) |
| Claude Code | ACP adapter `@agentclientprotocol/claude-agent-acp` (Apache-2.0, ACP organization, not Anthropic) **or** a narrow supervisor over the Agent SDK — chosen in S4; user's own API key (D29, D45) | `claude -p` as the only interactive channel; capturing the live TUI |

Shardrail has its own session model. ACP is the shared language for Grok and Hermes and a candidate for Claude. Codex stays on its app-server because that protocol is richer than ACP and is documented as the way to embed Codex in a product. Shared capabilities are projected into one model; provider-specific capabilities are kept, not flattened.

## 2. Adapter contract

- Capabilities are negotiated at `initialize`; static per-version tables are hints only. The core never calls a method the capability set lacks.
- **ACP version (D35).** The ACP client is dual-stack: it requests `protocolVersion: 2` and accepts a v1 selection (the Rust SDK provides a v1/v2 router, EV-22). The normalized model follows v2 semantics — turn end is a foreground `state_update: idle` with a stop reason, the `session/prompt` response only acknowledges message insertion, messages/tool calls/plans are upserts by id — and the v1 path synthesizes the same events from the v1 prompt response. v2 removes `session/load` (→ `session/resume` with `replayFrom`), `session/set_mode` (→ config options) and client `fs/*`/`terminal/*`. In v1 the following are now stable and preferred when advertised: `session/resume`, `session/list`, `session/close`, `session/delete`, `$/cancel_request`, elicitation, optional `messageId` (EV-23).
- **Session config options** (`session/set_config_option`, `config_option_update`) are the ACP channel for mode, model and permission-mode knobs. Approval-relevant options are set at session start and verified from the response; an agent-initiated change (`config_option_update`, `current_mode_update`, a `switch_mode` tool call) is a policy event (06 §3a), journaled and shown, never silently routed.
- Mandatory minimum: `start`, `prompt`, `stream`, `cancel`, `approve`, `health`. Optional: `steer`, `resume` (without replay), `load` (with replay), `fork`, `list_history`, `read_history`, `concurrent_sessions_per_process`.
- Normalized events: `session_started`, `turn_started`, `text`, `thought`, `tool_started`, `tool_updated`, `permission_requested`, `permission_resolved`, `plan`, `usage`, `turn_finished`, `session_degraded`, `notice`; each tagged ephemeral or durable (04). Fields without an equivalent are not invented; provider-specific data goes to `provider_ext`.
- ACP agents emit no "item completed" for message text; the adapter synthesizes completion when the update type changes, a tool call starts, or the `session/prompt` response arrives.
- **The ACP client never declares `fs/*` or `terminal/*` capabilities on v1 connections (D7); v2 has no such client surface.** Otherwise the agent could ask Shardrail itself to write files and run commands outside the provider's sandbox. File reading for the UI is done by the workspace service. v2 agent-owned display terminals (`terminal_update`, `terminal_output_chunk`) are display-only and rendered through the safe ANSI parser (06 §5).
- **Unknown requests are refused.** Every unknown server request gets an immediate refusing response (decline / empty grant / JSON-RPC error) plus a `notice`; unknown notifications become `notice`. *Why:* an unanswered request blocks a turn forever, and Codex already has request types (permission grants, MCP elicitation, tool user-input) that the first design did not model. **Known requests that act as approvals are modelled as approvals, not as "user input":** Codex `tool/requestUserInput` used for app/connector tool approvals, Codex `mcpServer/elicitation/request`, ACP elicitation that gates an action. Provider auto-resolution hints (Codex `autoResolutionMs`) are ignored — expiry is Shardrail policy (05 §6).
- **Approval options are classified** (D19): `once`; `widening` (persistent or session-wide rules: ACP `allow_always`/`reject_always`, Hermes `allow_always`/`allow_session`, Codex `acceptForSession`, `acceptWithExecpolicyAmendment`, `item/permissions/requestApproval` with `scope: "session"`, Codex network approvals — one answer may unblock several queued requests to the same destination); `boundary-breaking` (actions outside the sandbox, including side-effecting MCP tool calls whose server runs outside the provider sandbox, R42). Unknown kinds fail closed to `widening`, or `boundary-breaking` if they indicate sandbox/permission changes.

## 3. Compatibility policy (D24)

| Class | Behavior |
| --- | --- |
| `tested` | normal |
| `untested-newer` | starts with a warning; strictest supported sandbox; `widening`/`boundary-breaking` options hidden; allow-all disabled; shadow schema validation logs divergences |
| `known-bad` | refused without explicit override |

Product builds never opt into experimental surfaces (Codex `capabilities.experimentalApi`) — **no exceptions (D36)**. Consequently Shardrail does not use Codex `thread/backgroundTerminals/*` (experimental, `osPid` nullable, EV-03); background terminals are handled as tracked descendants by containment (06 §8). The Codex JSON Schema generated from the pinned CLI is stored in the repository and checked in CI; generating a schema from the user's binary is optional and diagnostic only. *Why:* the first design refused any unknown version, which would turn every routine provider update into an outage for a solo maintainer.

**Classification key (revised, 15 S7).** Classes are assigned per **protocol fingerprint**, not per binary semver: ACP negotiated `protocolVersion` + advertised capability set + adapter major version; Codex schema hash of the pinned stable surface. A new binary whose fingerprint equals a tested one is `tested`. *Why:* the Claude ACP adapter went from 0.24 to 0.93 in about seven months (EV-29) and Codex/Grok ship as often; exact-version classes would keep users permanently in strict mode.

## 4. Resume and replay (D33)

- Prefer resume without replay (ACP `session/resume` when advertised; Codex `thread/resume`).
- On ACP `session/load` (which must replay the whole conversation, EV-01): if Shardrail's journal has no known gap, the replay is discarded (used only to restore provider state) and one `provider_reloaded` marker is journaled. If a gap is known, the replay is shown as a separate, labelled "provider history" view and never merged.
- *Why:* the first design de-duplicated by provider event IDs, but ACP message IDs were optional, so duplicates could not be ruled out. Update (EV-22, EV-23): `messageId` is now stable-optional in v1 and required in v2, but the v2 spec itself says agent/thought ids may change across reconnects and advises rebuilding rather than merging replayed history — so the no-merge rule stands.
- ACP v2: `session/load` is replaced by `session/resume` + `replayFrom: {type: "start"}`; the same discard-or-separate rule applies. Every successful v2 resume is preceded by a current-state snapshot (`state_update`), which the engine uses instead of guessing the turn state.

## 6. Per-provider policy

**Codex.** Separate `codex app-server` child per session until S1 rules otherwise; no shared daemon/proxy. Default policy `workspace-write` + `on-request`; `danger-full-access` with `approval never` requires a separate confirmation phrase. `thread/shellCommand` is not bound to any button. Approval-relevant settings are pinned at launch with documented `-c` overrides, and **`approvalsReviewer: "user"` is sent on every `thread/start`, `thread/resume` and `turn/start` and checked in the response** (D37) — otherwise approvals may be routed to Codex's automatic reviewer and never reach Shardrail. Background terminals are not terminated through the experimental protocol methods (D36); containment kills them on termination. App/connector tool approvals arriving as `tool/requestUserInput` are approval records; `autoResolutionMs` is ignored. **Terms:** Codex documentation states that app-server authentication has never been permitted for commercial or hosted services (EV-03, EV-24). Shardrail is internal-use only (D45): it drives `codex app-server` with the user's own local Codex login and never drives the login itself; a move to commercial/hosted/third-party distribution reopens U25 before release (R46). Shardrail does not link Codex sources; types are generated from the schema. `--analytics-default-enabled` is never passed. `clientInfo.name` is reported to OpenAI compliance logs (known to the single user; user-facing privacy notes deferred, 09 §5). Shardrail offers to pre-create a protected `.codex/` directory (Codex protects it only if it exists) when a workspace is marked trusted; default no (U20, owner 2026-10-19).

**Claude.** Channel per S4. Starting Claude in an `unknown` workspace is forbidden; in `unknown`/`restricted` the session runs with `settingSources: []`, auto memory and connectors disabled; in all trust states approval-relevant settings (permission mode) are pinned at launch — **`permissionMode: "default"` is always passed explicitly**, because an omitted mode may start in `auto` (EV-25) — and permission-mode changes reported by the SDK/adapter are policy events (06 §3a). In `trusted` workspaces, allow rules from user/project settings files skip `canUseTool` silently; the effective allow rules are shown per session as "pre-approved by Claude settings" (06 §3a). `bypassPermissions` is never a default. Branding follows the SDK rules: the provider is labelled "Claude Agent" (or "Claude" inside an "Agents" menu), never "Claude Code". **Usage terms:** Anthropic's Agent SDK documentation says that, unless previously approved, third-party developers may not offer claude.ai login or rate limits for their products, including agents built on the SDK, and directs them to API-key authentication (EV-04). Owner decision (U9, 2026-10-19; D29, D45): Shardrail is internal-use only, and Claude runs through the Agent SDK / `claude-agent-acp` with the **user's own Anthropic API key** — no claude.ai login is offered in the app and no tokens are collected or brokered. No request to Anthropic is needed now; a move to commercial/hosted/third-party distribution reopens U9 before release (R46). Anthropic's legal page (EV-26) additionally distinguishes running the **unmodified** Claude Code binary, into which the end user signs in with their own subscription through Anthropic's flow (permitted, including on platforms that host Claude Code), from offering claude.ai login inside a third-party app or intermediating credentials (not permitted); the unmodified-CLI path is not used, because it offers no official two-way approval channel beyond the SDK. The adapter package is `@agentclientprotocol/claude-agent-acp` (renamed from `@zed-industries/claude-agent-acp` at 0.24.0, EV-29).

**Grok.** `grok agent stdio`, always started with an explicit `--sandbox <profile>` (Grok's own default is `off`). Default Shardrail profile for a new workspace `workspace`; user may tighten to `read-only` or `strict`; `off` requires separate confirmation. **Sandbox caveats (EV-27, R34):** every profile can write `~/.grok/` (Grok's own configuration, rules and sandbox profiles), and a project-level `.grok/sandbox.toml` lies inside the writable workspace — so an agent can change its own policy for *later* sessions; and if the sandbox cannot be applied Grok logs a warning and continues **unsandboxed**. Therefore: (1) the session is refused unless sandbox application is positively confirmed at start (probe or Grok's sandbox event log; mechanism chosen in S2) — fail closed; (2) hashes of `~/.grok` approval/sandbox config and `.grok/sandbox.toml` are snapshotted before every turn (06 §3, D20 revision); (3) Grok is no longer assumed to be the "sandboxed" Phase 1a provider — the first provider is chosen from S1-lite/S2 results (D40). Network deny cannot be promised on macOS. Grok's `auto` permission mode is shown only if S2 confirms requests still reach `session/request_permission`. Auto-update is suppressed for the spawned process with the documented `--no-auto-update` / `GROK_DISABLE_AUTOUPDATER`.

**Hermes.** `hermes acp` with the curated `hermes-acp` toolset. Browser tools are not set up by Shardrail. The effective toolset (default includes web/browser tools and `execute_code`) is shown per session; Shardrail does not edit `~/.hermes/config.yaml` and only recommends changes. `allow_always` is labelled as a permanent Hermes rule; `allow_session` as session-wide. Shardrail's approval expiry must not exceed Hermes' `approvals.timeout`. Hermes routes only dangerous terminal commands to the ACP host; **file edits never request approval** (EV-06, EV-31) — the session shows a persistent "file edits without approval" indicator, and Hermes is **not in Phase 1** (U26, D48, owner 2026-10-19); if ever added, the indicator is a permanent banner.

## 7. Differences that must not be flattened

- Codex sandbox and approval policy are two axes; Grok sandbox profile and permission mode are two different axes. The UI shows both, never one "autonomy" slider.
- Claude `auto` is a classifier; Grok `auto` in a non-interactive session blocks what its classifier rejects without asking. Shardrail, as an ACP client, provides the human channel.
- Cost: Grok reports ticks and may omit cost; Claude reports an estimated `total_cost_usd`; Codex cost fields unconfirmed. Missing data shows "no data", never zero.
- Claude cancel via SIGTERM corrupts the turn: the supervisor sends the protocol cancel, waits, and only then stops the process.

## 8. Provider updates

Shardrail never updates providers. Where an official flag exists (Grok), auto-update is suppressed for spawned processes. Elsewhere the compatibility policy (§3) is the protection. After the user updates a provider, Shardrail re-checks the version.
